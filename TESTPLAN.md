# Test plan

This document captures the [TestRPG acceptance criteria](https://github.com/micheltestcoders/testrpg) and shows which automated tests cover each one.

## Test design philosophy

Tests are written against the acceptance criteria below as the **primary spec**. Where the AC is silent on a detail (for example the exact response shape of `GET /api/builds`, or the validation rules for the login form), we fall back on the application source code (Zod schemas, type definitions, component logic) as a **secondary spec source**, and we make that explicit in code comments and in the observations section below.

Passing tests confirm the implementation matches the spec. Failing tests surface mismatches as findings. **Some tests in this suite are intentionally red because of such a mismatch** — the red state IS the finding (see `LoginTest.invalidEmailShouldShowCustomZodError` and `GetBuildsTest.getValidBuildHasExactDocumentedShape`).

We avoid asserting on observed behavior alone: locking in "this is what the implementation does today" without a documented or source-grounded spec creates tests that duplicate the implementation rather than verify it.

## Acceptance criteria

Quoted from the TestRPG project README (`micheltestcoders/testrpg`).

### `/play`

1. Character name has to be at least 3 characters and at most 20 characters.
2. Changing the character build type changes the stats (strength, agility, wisdom, magic).
3. Clicking the click-task button 5 times levels up the character and shows a confirmation message.
4. Selecting a file in the upload-task levels up the character and shows a confirmation message.
5. Typing `Lorem Ipsum` in the typer-task levels up the character and shows a confirmation message.
6. Moving the slider all the way to the right levels up the character and shows a confirmation message.
7. After completing each task, the related input is set to disabled.
8. Completing a task shows a toast notification that disappears automatically after 3 seconds.

**Bonus**: typing `all your base are belong to us` in the typer-task before completing it activates berserk mode, which makes every subsequent level-up max out the stats.

### `/inventory`

1. The page shows a build selector with the four available builds (thief, knight, mage, brigadier).
2. Selecting a different build resets the equipment slots and repopulates the bag with items for that build.
3. The bag contains four items: two weapons and two armor pieces for the selected build.
4. There are two weapon slots and two armor slots, allowing all four items to be equipped simultaneously.
5. Dragging a weapon item onto a weapon slot equips it, removes it from the bag, and shows a success toast.
6. Dragging an armor item onto an armor slot equips it, removes it from the bag, and shows a success toast.
7. Dragging an item onto the wrong slot type shows an error toast and leaves the item in the bag.
8. Once all four items are equipped the bag shows an "All items equipped" message.

### `/api/builds`

Documented separately on the `/api` page of the application. Two endpoints:

- **GET** `/api/builds` with an optional `?build=<name>` parameter (valid values: thief, knight, mage, brigadier).
- **POST** `/api/builds` with a JSON body matching `{build: {name, strength, agility, wisdom, magic}}`. Name cannot be an existing name; no skill higher than 10; sum of all skills max 10.

## Observations during development

These came up during exploratory testing while building the automation. They are not all bugs; some are spec inconsistencies or design observations worth discussing in the case study interview.

- **Brigadier predefined build violates the POST sum rule.** Brigadier's stats sum to 11 (3+1+6+1), but the POST endpoint rejects any user-submitted build whose stats sum to more than 10. Either Brigadier is grandfathered or the rule is intended only for user submissions; the predefined Brigadier could not be created via the POST endpoint as a regular user.
- **GET response shape diverges from the documented schema for predefined builds.** The `/api` documentation defines a build as `{name, strength, agility, wisdom, magic}` (the POST schema is the only place where build shape is documented). When GET returns a predefined build (thief, knight, mage, brigadier), the response object has four undocumented fields (`weapon`, `upgradedWeapon`, `armor`, `upgradedArmor`) and is missing the `name` field that the documented schema requires. POSTed builds round-trip correctly with the documented shape, only predefined builds break it. `GetBuildsTest.getValidBuildHasExactDocumentedShape` asserts the documented shape strictly and currently fails for all four predefined builds; that failure IS the finding.
- **Clicker button text says "Click me 1 times"** when one click is remaining. Should be "1 time" (singular). Minor copy bug.
- **Inventory type-mismatch error message has a grammar oversight for armor.** The source in `pages/inventory.tsx` builds the toast text as `` `A ${item.type} cannot be equipped in the ${slot.type} slot.` `` with a hardcoded "A" article. For weapon items this reads correctly ("A weapon cannot be equipped..."), but for armor items the result is "A armor cannot be equipped..." which is grammatically wrong ("An armor" would be correct). Small copy bug, same family as the "Click me 1 times" issue.
- **The typer input uses inconsistent case handling for its two recognised strings**: the AC5 trigger "Lorem Ipsum" is matched strictly case-sensitive (verified by the parameterized negative tests in `TyperTest`), while the bonus Easter egg trigger "all your base are belong to us" is matched case-insensitive (via `.toLowerCase()` in the source). Two checks living in the same component with different matching rules.
- **The email field has two validation layers and the custom error is rarely reachable**: the input has `type="email"` so the browser runs HTML5 validation first and shows a native tooltip (browser chrome, not in the DOM, locale-dependent) for clearly invalid emails. Only when an email passes browser validation but fails Zod's stricter regex would the developer-defined "This should be an email address" message appear. In practice this means the custom error is almost never shown to users, which is a confusing UX setup.
- **Login is fake by design** and the dialog says so: "Any combination of email and password will work". The form only validates that the email matches a basic email regex (via Zod) and that the password is non-empty. There is no backend authentication, rate limiting, account lockout, or password complexity. The "logged in" state is held in a Zustand store persisted to localStorage under key `login-store`, so it survives page reloads. Worth flagging as observations even though they are by design for a demo app.
- **The gameplay flow is fully client-side**: character creation, build selection, and all four `/play` adventures are React state changes only. No API calls are made during these flows. The `/api/builds` endpoint exists as an independent surface for the API test cases.
- **The "occupied slot" inventory error is in the source but not in the AC.** `pages/inventory.tsx` rejects a drop on an already-equipped slot with `"This slot is already occupied."`, but the `/inventory` acceptance criteria are silent on this case. Our `InventoryTest.equippingOnOccupiedSlotShowsErrorToast` asserts the source-defined behaviour; under the project's "test against the spec" rule this is one test that knowingly tests an undocumented behaviour, with that exception noted here.
